# ETF Builder

DIY S&P 500 / NASDAQ-100 basket builder. Static HTML/CSS/JS, no build step, no backend.

## Run it

```
python3 -m http.server 8743
```

Then open http://localhost:8743. (Needs a real HTTP server, not `file://`, because `index.html` fetches the JSON files in `data/`.)

## Deploying

Works as-is on GitHub Pages (or any static host) with zero changes — no build step, no backend. All paths in `index.html` (`css/styles.css`, `js/app.js`, `data/*.json`) are relative, so it doesn't matter whether Pages serves it at the domain root or under a project subpath like `username.github.io/etf-builder/`. Just push the repo and enable Pages on the branch/folder in repo settings. Pages serves over real HTTPS, so the `fetch()` calls for the JSON data work fine there — this is only a problem locally over `file://`, not once it's deployed.

## Test it

```
npm test
```

Runs `node --test` over `test/*.test.js` — no dependencies, just Node's built-in test runner. All portfolio-construction math (`js/portfolio.js`) and tax simulation (`js/tax.js`) is pure functions, unit-tested in isolation from the DOM.

## Refreshing the data

`data/sp500.json` and `data/nasdaq100.json` hold real constituent data (~500 / ~100 names, symbol/name/sector/market cap), generated by:

```
node scripts/fetch-constituents.mjs
```

This pulls S&P 500 membership + name + GICS sector from Wikipedia's "List of S&P 500 companies", NASDAQ-100 membership + name + market cap from Nasdaq's own public list-type API, and market cap (both indices) + a sector fallback for NASDAQ-100-only names from Nasdaq's public stock-screener API — no key, no scraping library (see Q5). It's not wired to run automatically; re-run it manually when you want a refresh (index membership only changes a few times a year via quarterly reconstitution, so this doesn't need to be frequent). One symbol (`BF.B`, Brown-Forman) is dropped rather than included with a fabricated market cap — none of the three sources checked have a market cap for it; see the script's warning output.

`data/returns.json` (1y/5y/10y return stats + a sparkline series per ticker) is generated by:

```
node scripts/fetch-returns.mjs
```

This one *does* run automatically — see `.github/workflows/update-returns.yml`, a monthly GitHub Actions cron job that regenerates it and commits the result back to `main`.

## Q5 — Are there public APIs for S&P 500 / NASDAQ-100 data?

Short answer: **not for free, directly from the index providers.** S&P Dow Jones Indices and Nasdaq both license constituent + weight data commercially — there's no free official "give me the current S&P 500 weights" endpoint. But you don't need one — the pieces above compose into something just as good:

1. **Wikipedia's "List of S&P 500 companies"** — free, community-maintained (sourced from SEC filings), has ticker/name/GICS sector. No market cap or weight, though — that's the gap the next source fills.
2. **Nasdaq's public API** (`api.nasdaq.com/api/screener/stocks` and `api.nasdaq.com/api/quote/list-type/nasdaq100`) — the same JSON that backs Nasdaq's own screener and NASDAQ-100 listing pages. Whole-market symbol/name/market-cap/sector in one call, no key, no auth. This is what actually makes the app's `marketCapB`-driven weighting work — Wikipedia alone can't provide it.
3. **ETF holdings files** (iShares `IVV`, Invesco `QQQ`) were the original plan here, since the ETFs track these indices almost exactly and their holdings amount to index weights. In practice both are behind bot-detection walls (iShares serves a JS challenge page instead of the CSV) that aren't worth building a solver for — treat this as a dead end for a script like this, not a recommendation.
4. **Free-tier financial data APIs** — Financial Modeling Prep, Finnhub, Alpha Vantage, EOD Historical Data, Tiingo. Most gate the constituents endpoint behind a paid tier or rate-limit hard enough that a manual refresh script is still the practical pattern.
5. **Paid/official** — S&P Capital IQ, Nasdaq Data Link's paid index sets — only worth it if accuracy/compliance actually matters, which it doesn't for a personal planning tool.

For historical prices (return calculations), the equivalent finding: Stooq's CSV endpoint now requires solving a client-side proof-of-work challenge before it responds — also a dead end, for the same reason (not worth building a bot-detection bypass for). Yahoo Finance's unofficial chart endpoint (`query1.finance.yahoo.com/v8/finance/chart/{symbol}`) works cleanly with monthly adjusted-close data and no key, and is what `scripts/fetch-returns.mjs` actually uses.

## Q6 — Would a Python backend actually help?

For this app, no — the cost doesn't clear the bar.

**What a backend would buy you:**
- Hiding an API key, if you ever use a provider that requires one for live quotes.
- Scheduled background refresh instead of manual/local script runs.
- Heavier computation that doesn't belong in the browser — e.g. a real backtested tracking-error calculation over years of daily prices for hundreds of stocks (that's real data + real compute, not something to ship as a client-side fetch).
- Aggregating multiple paid data sources behind one internal API.

**What it costs you, solo:**
- An endpoint to deploy, monitor, and patch.
- Auth/rate-limiting to keep it from being scraped or abused if it's public.
- Cold starts and a recurring (small but nonzero) cloud bill.
- One more thing to maintain when nothing about this app's core value — pick a basket, see coverage/concentration, compare DIY vs ETF tax — actually needs server-side compute. All of that math runs instantly in the browser on ~100 rows of data.

**Where the line actually is:** skip the backend entirely for now. If you later want the backtested tracking-error feature (the one item on the backlog that's genuinely compute/data heavy), the right shape is still not "a Lambda the public can hit" — it's a scheduled job (GitHub Actions cron, or a local script you run monthly) that computes results and writes a static JSON file, same pattern as the data refresh. A deployed, publicly-reachable backend only earns its keep if you need *live*, *on-demand*, *user-specific* computation — none of which this app needs yet.
